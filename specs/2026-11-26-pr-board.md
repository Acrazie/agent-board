# Spec: pr-board

A Claude Code mod that shows the user's open weeki-io pull requests in a side pane, flags new feedback, and shows review details inline, so nobody has to check GitHub or email for PR status.

## 1. Starting point

**Why.** The user's pull requests are spread across 45 weeki-io repositories. Their state (draft, open, changes requested) and every new review only reach the user through GitHub's web UI or notification emails. Both have to be checked by hand, away from where the work happens.

## 2. Goals and non-goals

**Goals**
1. A mod at `plugins/pr-board` in agent-board opens a pane listing the user's open PRs in weeki-io, in two sections:
   - **À corriger**, shown first: PRs whose `reviewDecision` is `CHANGES_REQUESTED`. When GitHub reports no `reviewDecision` (the base branch requires no review, as with stacked PRs), a PR is there when at least one reviewer's latest decisive review (`APPROVED`, `CHANGES_REQUESTED` or `DISMISSED`; `COMMENTED` does not count) is `CHANGES_REQUESTED`; a later approval or dismissal by that reviewer takes it out. A non-null `reviewDecision` is the only rule.
   - **Ouvertes**: every other open PR, each marked *draft* or *prête*.
2. A PR that has received a review or comment from someone else since the user last opened it in the pane carries a **nouveau** badge.
3. Clicking a PR expands it in the pane. The expansion shows the reviews and comments (author, text, file and line when inline) and a link to the PR on GitHub. Expanding the PR clears its badge.
4. When `gh` is logged out or fails, the pane shows a clear error. It never shows an empty list that could pass for "no PRs".

**Non-goals**
- Merged PRs: the user removed them from scope.
- Reviews requested from the user, and PRs by other authors: not asked for.
- Repositories outside weeki-io.
- Any write to GitHub (merge, comment, re-request review): the mod only reads.
- Toasts or notifications: the badge is enough.
- A button that sends review text to Claude: rejected, because untrusted text would reach the model.
- A new token or secret, a web page, or publishing to the organization's plugin library.

## 3. Constraints

**Invariants**

| Invariant | Where it is enforced or detected | Machine or human |
|---|---|---|
| The mod runs only read-only `gh` commands, fixed in the code. The only values that may enter them are opaque GitHub ids and pagination cursors, validated against a strict pattern before any command runs; never human-written text (titles, bodies, names, paths). | `claude plugin validate` for the calls the module makes, plus a review by a fresh agent that never saw the build | machine + fresh agent |
| Review and comment text is display-only. It is never sent to the model, never executed, and never passed to a command. | Test with a crafted comment: it renders verbatim, and no `prompt.*` hook or `$.model` call fires | machine |
| No secret is stored. Access goes through the `gh` token in the keyring. | Test: `$.store` holds only the "seen" state | machine |
| The `agent-board` and `file-activity-tree` mods keep working unchanged. | `claude plugin validate .` and their existing tests | machine |

**Owned state.** The mod owns no irreversible effect. GitHub stays the source of truth. The only data the mod owns is the per-PR "seen" timestamp in `$.store`. Losing it only brings back *nouveau* badges.

**Worked examples**
- **Today's data:** `atlas#67` lands in *À corriger*. `atlas_frontend#18`, `atlas_api#7` and `notebook_api#6` land in *Ouvertes (prête)*.
- **Draft with changes requested:** it appears only in *À corriger*, still marked draft. A PR is never listed in both sections.
- **No open PRs:** the pane says there are none, worded differently from the error in goal 4.

**Defaults (confirmed)**
1. Data refreshes when the pane opens, then every 2 minutes, and on demand through a refresh button.
2. The pane opens with a `/prs` command and never opens by itself.
3. *Nouveau* means a review or comment by someone other than the user, posted after the user's last expansion of that PR in the pane. The "seen" state is local to this machine.
4. A PR stays in *À corriger* while GitHub reports `CHANGES_REQUESTED`, even after the user pushes, until the reviewer approves or dismisses the request.
5. Within each section, PRs are sorted by most recent update first.
6. The expansion shows at most the 20 most recent reviews and comments, newest first.

**Stop and ask** when:
- `$.process.run` does not work in the desktop app;
- `reviewDecision` turns out not to identify PRs that need changes;
- any goal seems to need a write to GitHub.

**Left to the agent:** internal naming, pane layout, GraphQL or REST, the format of recorded `gh` fixtures, and how the `/prs` command is registered.
